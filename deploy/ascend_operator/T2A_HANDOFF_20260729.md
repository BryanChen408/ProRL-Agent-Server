## 一、怎么拿到最全的上游

上游分散在**三个来源**,少任何一个都会踩坑。

### 1. skills 主仓

```bash
git clone https://gitcode.com/cann/cannbot-skills.git
```

我们用的 plugin:`plugins-community/tilelang2ascendc-ops-generator`。

**依赖闭包 = 22 个 skill**,来自 `plugin.json` 的 `dependencies`:

```
tilelang2ascendc-ops-generator/skills/     6 个(tilelang2ascend-*)
ops-direct-invoke-skills/skills/          16 个
```

⚠️ **`init.sh` 只按 `AGENTS.md` frontmatter 装 12 个,不看 plugin.json 的 dependencies**。
按 frontmatter 装会缺 10 个,包括 `torch-ascendc-op-extension`(见下,它很关键)。

官方两条装法(quickstart.md):

```bash
# 首选:Plugin Marketplace
/plugin marketplace add https://gitcode.com/cann/cannbot-skills.git
/plugin install tilelang2ascendc-ops-generator@cannbot

# 备选:init.sh
cd plugins-community/tilelang2ascendc-ops-generator && bash init.sh project claude
```

`[对比]` **两条装法只有 `init.sh` 会 clone asc-devkit**(Step 4)。`/plugin install` 不会 ——
该 plugin 的 `plugin.json` 没有 postinstall,目录下只有 `init.sh` 里有 `git clone asc-devkit.git`。

`[对比]` init.sh 用**软链**把 skill 挂进 `.claude/skills/`(`ln -sfn $(realpath …)`),
skill 脚本 `.resolve()` 后仍在 clone 里,所以它们**按层数反推仓库根**的写法在上游成立;
我们是实拷进容器,那个前提不成立 —— 这是三处越界 import 的根因(见第三节)。

### 2. asc-devkit(算子开发资料仓)

```bash
git clone --depth 1 --branch 9.0.0 https://gitcode.com/cann/asc-devkit.git
```

`[对比]` `$ASC_DEVKIT_DIR` 在 22 个 skill 文档里被引用 **46 次**,是出现最多的环境变量
(超过 `$ASCEND_HOME_PATH` 的 16 次),5 个 skill 直接依赖它;`ascendc-docs-search`
整个 skill 就是查它。

`[实测]` **分支要与本机 CANN 同版本,不要用 init.sh 默认的 master**:
拿两版文档的 API 名比对本机 CANN 9.0.0 的 9161 个头文件 ——

```
9.0.0  docs/api/context   1465 个 API 名 → 命中 1400 (95%)
master docs/zh/api        1873 个        → 命中 1552 (82%)
master 独有的 548 个       → 只命中 259  (47%)   ← 一半以上本机不存在
```

用 master 会让模型照着写出本机没有的 API。

`[实测]` 9.0.0 的布局是 `docs/api/context/`,而 skill 里写死 `docs/zh/api/` ——
在 clone 里建**相对**软链即可(绝对软链在容器挂载后会悬空):

```bash
cd asc-devkit/docs && mkdir -p zh && cd zh && ln -sfn ../api/context api
```

### 3. CANN 自带(不是仓,是安装)

`[实测]` `kernel_operator.h`(3 处)、`ascendc.cmake`、`asc/impl/*` 都在 CANN 安装下:

```
$ASCEND_HOME_PATH/x86_64-linux/asc/include/kernel_operator.h
$ASCEND_HOME_PATH/x86_64-linux/tikcpp/ascendc_kernel_cmake/ascendc.cmake
```

⚠️ 上游文档里的 `asc-devkit/docs/api/` 指的是 **① 那个 GitCode 仓**,不是 CANN 里同名的
`share/info/asc-devkit`(那只是安装记录)。我一度把两者混为一谈,判定"asc-devkit 不可用"
并写进覆盖区 —— 那条是错的,已撤回。

## 四、还没解决的(按严重度)

### 🔴 1. 单会话装不下上游设计的迭代次数

`[实测]` 上下文上限 262144 tokens ≈ 768 KB。实测所有 session 都堆到 **~300 KB 就停**:

```
评测 5 次的 session:累计 202~286 KB
评测 1 次的 session:累计 259~340 KB(前期探索吃掉了)
平均每次评测增长 ~145 KB → 17 次外推 2458 KB ≈ 839k tokens = 上限的 3.2 倍
```

`[对比]` 上游能做 17 次(A 类 5 + D 类 12)是因为它有**重入压缩**:主 agent 每轮用
「参数 + `resume_from` + `d_retry` + trace.md **摘要**」重新调 subagent,每轮上下文清零。

我们是单 agent 累积上下文、**compaction 实测 0 次触发**。所以 `def15438` 把
`generation_max` 5→17 **给不出 17 次** —— session 会在第 5-8 次耗尽上下文。

三条路:引入主 agent 层做重入(会把 subagent 绕过护栏的口子打开)/ 查 compaction 可行性 /
接受实测水位把预算定在 5-8。**未决。**

### 🟡 2. Mode B 不可用,模型仍须自备 CMakeLists

`[实测]` `t2a_modeb_probe.sh`:M1(Mode A)PASS,**M2(Mode B)FAIL** ——
自动生成的模板把 `op_host/*.cpp` 塞进 `ascendc_library(kernels)`,而 torch 的 include
只加给 `pybind11_lib`,host 侧 `#include <torch/extension.h>` 找不到。

所以 `6b651d0b` 的意义收窄为"对齐上游流程 + Mode A 等价"。

`[对比]` 上游有整套模板在 **`torch-ascendc-op-extension`** skill 里
(`templates/{CMakeLists_template.cmake, ops_template.h, torch_template.cpp, register_template.cpp}`
+ SKILL.md 的 Step 0-5 改造流程),形态正是我们判分要的 TORCH_LIBRARY 对接。

指路只有一条:`ascendc-direct-invoke-template/SKILL.md:105`「PyTorch 对接详见
torch-ascendc-op-extension skill」—— 而那个 skill **只在简单算子路径被调用**。
复杂算子路径(25/31 个算子)没有指路。**未决:要不要在覆盖区补一行门牌。**

### 🟡 3. 4 个 agent 与主 agent 层

`[对比]` 4 个 agent(architect/design-reviewer/developer/reviewer)仍未恢复。理由:
`Task` 不在 `disallowed_tools` 里 → 它们是**可派发的 subagent 类型**,而 subagent 拿的是
上游原文系统提示,不带覆盖区(不知道固定入口、禁 npu-smi、抢卡)。

`[对比]` 恢复后的 Phase 4-S 原文是"以 Developer 视角审查""以 Architect 视角回应",
是**同一 agent 的角色扮演**,全文无 `Task` 派发 —— 所以不恢复那 4 个文件也能走完 Phase 4-S。

中间选项:恢复 4 个文件 + 把 `Task` 加进 `disallowed_tools`(代价:也用不了 `Explore`
只读子 agent,实测本轮用了 9 次)。**未决。**

主 agent 层(`AGENTS.md`,245 行)**实际职责**已读全:D 类重入循环 + 返回后强制检查点
(防 subagent 以"API 限制/框架 bug"为由跳过修复)+ 高风险行为限制。除重入压缩外,
其余我们都有等价物。

### 🟢 4. 零散

- `archive_tasks/rms_norm/kernel/op_host/rms_norm.cpp:61` 用了全树/全 CANN 都没定义的

## 七、方法论(这轮最贵的教训)

我这轮翻车的结论**全是"查了一处就断言全局"**的归因判断:
`parents[5]` 归因、archive CMakeLists 可抄性、扁平布局来源、asc-devkit 可用性、
Mode B 能力、"上游没有 CMakeLists 模板"、"AGENTS.md 里有指路"(那是另一个 plugin 的)。

站住的**全是能跑一遍或能逐字对比的**:三处越界 import、闸门 D、`--repeats` 放大机制、
router 与 token ids、端口撞车、210 行缺失。

**建议下一个会话:归因类结论一律先全仓搜再说;结论标注证据等级;每轮 rollout 后固定读
2-3 条完整心流,不要只看聚合统计** —— 今天几个最关键的发现(agent 读用不了的模板、
`cat` 我们的脚本 209KB、烧评测预算调打包)都是读心流才出来的。
