# AscendC 性能实现模式

本文只补充性能设计知识。正确性通过前，先修正确性；正式性能结论仍以当前 Polar 固定
评测入口的结果为准，不另起 profiler 或计时流程。

## 先判断瓶颈，再改结构

按源码、shape/dtype 和固定入口的逐 case 延迟形成一个可验证假设：

- 搬运主导：重复 CopyIn/CopyOut、非连续访问、无效 padding 或 UB 往返过多；
- Vector 主导：逐元素标量操作、repeat 次数过小、同一中间结果重复计算；
- Cube 主导：M/N/K 分块不合适、L1/L0 搬运和计算没有重叠、尾块比例过大；
- 负载不均：工作单元少于核数、尾块集中在少数核、不同分支工作量差异大；
- 同步主导：每行/每 tile 的 barrier 或事件过多，队列深度不足，跨核等待串行化。

没有硬件计数器时只能把这些写成“待验证的优化假设”，不能把源码猜测当成已确认的
bound。一次只改一个结构因素，下一次固定入口复测。

## Tiling 与核间负载

- 先估算总工作单元，再决定使用多少核；工作单元太少时，盲目铺满核会增加调度和尾块开销。
- 尽量让各核的完整 tile 数接近；尾块不要全部落在最后一个核。
- tile 太小会被 launch、事件和地址计算开销吞掉；tile 太大则并行度不足或挤压 UB。
- 动态 shape 用分档或运行时计算，不按单个训练 case 写死 tile。
- 多分支算子按最大分支资源规划，但保留轻量分支的快速路径。

## UB、L1/L0 与双缓冲

- UB 预算同时包含有效数据、padding、累加器、临时结果和事件/队列需要的 buffer。
- 只有当 CopyIn、计算和 CopyOut 能够重叠，并且剩余容量足够时才使用双缓冲；
  双缓冲不是默认更快。
- Cube 算子分别规划 GM→L1、L1→L0、Mmad 和结果写回，避免只优化计算而让搬运成为新瓶颈。
- Vector 算子优先保持连续访问和整块搬运；对不连续布局，比较一次重排和直接跨步访问的总成本。
- buffer 生命周期要短而明确，避免为了复用导致额外同步或 alias。

## 搬运与流水

- 多行连续或规则 stride 的输入尽量批量搬运，减少每行 API 调用和事件配对次数。
- 完整对齐块走普通 DataCopy，尾部再走 DataCopyPad；不要让每个完整块都承担 padding 开销。
- 复制、计算和写回之间使用最小必要同步；`PIPE_ALL` 会让本可重叠的流水串行化。
- 跨 pipe 数据依赖用对应事件，单 pipe barrier 不能证明其他 pipe 已完成。
- 不在同一 stream 的顺序 kernel 之间随意插入 host synchronize；这会把设备流水变成串行。

## 算子类别的性能侧重点

| 类别 | 优先检查 |
|---|---|
| 归约/Norm | 归约维布局、FP32 workspace、批量行数、尾块和同步次数 |
| 重排/Gather/Scatter | 源行去重、索引表生成、连续写回、重复索引和原子写 |
| Sort/TopK | 多遍扫描次数、分段排序规模、tie 处理和标量计数 |
| 量化/复制 | clone 与 update 的流量比例、dtype 往返、scale/zp 常驻和写回布局 |
| Pooling/窗口 | 数据布局、窗口搬运、C 维对齐、反向累加和输出尾块 |
| MatMul/Cube | M/N/K 分块、L1/L0 复用、k-tail、Fixpipe 和 Cube 利用率 |

## 优化循环的证据纪律

1. 记录当前固定入口的正确性状态和逐 case 性能。
2. 找出拖慢整体指标的同类 case，而不是只优化最快 case。
3. 结合源码提出一个通用结构假设。
4. 只实施一项修改，确认源码确实变化。
5. 重新运行当前固定入口，同时检查正确性和性能是否都保留。
6. 如果没有改善，保留结果证据并撤回或换下一项假设。

性能优化不能通过修改 reference、case、精度阈值、warmup/repeats 或比较口径来获得；
这些内容属于固定评测契约。
